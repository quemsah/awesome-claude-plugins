# Что осталось сделать для переезда с n8n

Локальная реализация этапов 1–3 находится в ветке `migratefromn8n`. Этап 4 **не начинался**: Railway не настраивали, живой GitHub-обход не проводили, в `main` не публиковали, n8n не отключали. В этом checkout нет Git remote. Владелец решил выполнить развёртывание позже самостоятельно.

Подробные требования и критерии: [`migratefromn8n/04-railway-cutover.md`](../migratefromn8n/04-railway-cutover.md), [`migratefromn8n/05-acceptance.md`](../migratefromn8n/05-acceptance.md). Команды, переменные и восстановление после прерванного запуска: [`crawler/README.md`](../crawler/README.md). Этот список не заменяет проверку этих документов перед развёртыванием.

## 1. Подтвердить цель и подготовить Railway

1. Установить и проверить Git remote для **нужного** `owner/repo`. Сверить целевую ветку, права токенов и существующее расписание n8n. Не считать старый URL из экспорта n8n подтверждением текущей цели.
2. Создать отдельный crawler cron-сервис с Root Directory `/crawler`, Node 24, сборкой `npm ci && npm run build`, одним экземпляром и постоянным Railway volume в `/data`. Задать `DB_PATH=/data/catalog.sqlite`, `CRAWL_INTERVAL_HOURS=24`, `GITHUB_READ_TOKEN`, `PUBLISH_ENABLED=false`. Пару `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` задавать вместе, если нужны уведомления. На пилоте токен Git-записи не нужен; секреты указывать только в Railway.
3. Проверить на Railway, что `/data` действительно смонтирован как отдельный volume: crawler откажется открыть БД без него. Настроить Watch Paths `/crawler/**`, отдельно проверить Git-деплой сайта из `/ui/**`. Cron `0 4 * * *` UTC оставить выключенным до контролируемого полного пилота: после dry-run метка последней **публикации** не обновляется, поэтому включённый cron может повторять дорогой обход ежедневно.

## 2. Загрузить историю и защитить БД

1. Обеспечить доступ сервиса к `n8n/c2-claude-plugins.csv` и `n8n/c2-stats.csv`. При Root Directory `/crawler` соседняя папка `n8n/` недоступна в сборке; нужен согласованный способ доставки файлов в `crawler/seed/` либо в среду с тем же volume. Если временно коммитить копии CSV, перед коммитом проверить их на закрытые данные и помнить, что удаление из дерева не удаляет их из истории Git. Не копировать экспортированные n8n-workflow и токены.
2. На **самом Railway-сервисе с подключённым volume**, не через локальный `railway run`, выполнить однократный `node dist/cli.js seed --repos seed/c2-claude-plugins.csv --stats seed/c2-stats.csv`. Повторный старт может использовать `seed-if-empty`. Командой `node dist/cli.js inspect` подтвердить `integrity: ok`, 52 760 репозиториев, 41 169 непустых URL, 11 591 пустых URL и 264 исторические записи stats.
3. Настроить резервное копирование Railway volume, снять backup до обхода и испытать восстановление на тестовом окружении без записи в production. После восстановления повторить `inspect`, а последний `run_id` сверить отдельным read-only запросом к таблице `runs`: команда `inspect` его не выводит. Не удалять исходные CSV или старые выгрузки до проверки restore.

## 3. Провести полный сухой пилот

1. Оставить n8n работающим и `PUBLISH_ENABLED=false`. Сначала проверить сборку native SQLite и короткий запуск с подставным GitHub API, затем выполнить **один полный** `node dist/cli.js crawl --dry-run --force` по настоящему GitHub из Railway. Заложить много часов: минимум порядка 16 часов при доступной квоте, фактическое время неизвестно.
2. Сохранить `run_id`, время, предупреждения о неполных/насыщенных size-диапазонах, числа готовых/пропущенных/удалённых записей и строку `github_rate` с количеством попыток, ожиданием и остатками квот отдельно для `code_search` и `core`. Измерить RAM, CPU, объём volume/backup и месячную стоимость по фактическому запуску; сравнить с n8n.
3. Перед сверкой выполнить `node dist/cli.js export --run-id <id> --output-dir /absolute/new-directory`. Команда повторно проверяет хеш и пишет README и оба JSON в новый каталог вне `ui/` без Git API. Не подменять опубликованный сайт черновиком. Затем сверить экспорт с последней публикацией n8n по ID и URL, объяснить судьбу 211 исторических URL без полного набора полей, подтверждённые 404, новые результаты и предупреждения поиска. Любая необъяснённая разница блокирует переключение. Проверить сайт, `/api/catalog`, `/stats`, страницы, sitemap и feed на новых данных в отдельном staging checkout/окружении без записи в `main`. Запустить команды и матрицу из `05-acceptance.md`.
4. Проверить Git API на согласованной тестовой ветке **только с отдельным разрешением на запись**. Провести Go/No-Go по корректности данных, backup/restore, длительности cron и стоимости. При No-Go оставить n8n и Git-публикацию как есть.

## 4. Отдельно разрешить публикацию и переключение

После успешного пилота и явного разрешения владельца задать **отдельный** `GITHUB_PUBLISH_TOKEN`, `GITHUB_REPOSITORY=owner/repo`, `GITHUB_BRANCH=main`, Telegram-пару и `PUBLISH_ENABLED=true`. Если каталог после проверки не изменился, публиковать проверенный черновик командой `node dist/cli.js publish --run-id <id>`, а не запускать повторный полный обход. Проверить один нефорсированный коммит с README и обоими JSON, деплой UI, API/страницы/статистику и Telegram с тем же SHA. До отключения n8n настроить независимое от cron-сервиса оповещение о слишком долгом активном процессе и отсутствии прогресса. Сигнал о `active_run`/`publication_locked` отправляется только при запуске CLI и не заменяет этот контроль. Только затем остановить orchestrator n8n и включить обычное расписание crawler с командой `node dist/cli.js crawl`. Проследить следующий запуск до и после 24-часовой границы и записать результаты в протокол из `05-acceptance.md`.

Если обход остановился, **сначала** убедиться, что прежний процесс не работает, и сделать backup. Для прерванного crawl есть `recover-crawl --run-id <id> --confirm-stopped`; для неоднозначной Git-публикации есть `publish --run-id <id> --recover --confirm-stopped` после проверки pending SHA. Пока SQLite-lease публикации не согласован, новый обход намеренно блокируется. Не удалять lease вручную и не выключать n8n раньше проверки публикации. Порядок отката описан в `04-railway-cutover.md`.
