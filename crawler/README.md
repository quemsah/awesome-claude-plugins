# Crawler package

This package is separate from `ui/` and requires Node.js 24. Run `npm ci` from `crawler/`, then `npm run build` to create `dist/cli.js`. The Railway service uses `/crawler` as its root directory and runs the built CLI.

`npm run typecheck`, `npm run lint`, and `npm run test` validate this package. Set `DB_PATH` before running `npm run seed -- --repos <path> --stats <path>`, `node dist/cli.js seed-if-empty`, or `npm run inspect`. Seed defaults to `seed/c2-claude-plugins.csv` and `seed/c2-stats.csv` relative to the crawler working directory. For local imports, provide explicit paths to the CSVs in `../n8n/`; the Railway `/crawler` build cannot access that directory. The two seed files are needed only for the first import, not for subsequent `seed-if-empty` runs. Do not check temporary seed copies or local SQLite databases into Git.

`seed` validates both CSV headers and rows, imports both tables and their SHA-256 hashes atomically, and refuses to overwrite partial or differently seeded data. It preserves signed legacy repository counters; new enrichment still rejects negative counters. On malformed CSV input, CLI errors include the table, row and column, but not the cell value or filename. `seed-if-empty` skips an existing complete import but rejects a partial import or missing CSVs on an empty database. `inspect` reports aggregate counts, ID ranges, negative legacy counter totals by field and affected row count, import state, and SQLite integrity without exposing row data.

`npm run crawl -- --dry-run --force` performs a full crawl, prepares and persists a draft, but never calls Git's write API or claims publication. `npm run crawl` checks `last_published_at` in SQLite and skips the crawl before the 24-hour interval; `--force` bypasses only the interval, never the active-run or publication lock. The daily cron can delay the next start if a crawl runs past its next scheduled time. An unseeded database cannot crawl. `PUBLISH_ENABLED=false` is the default pilot mode: even without `--dry-run` it prepares a draft only. With `PUBLISH_ENABLED=true`, an ordinary due crawl publishes the prepared draft after successful search and enrichment. `npm run publish -- --run-id <id>` publishes an already prepared, unchanged draft without repeating the crawl; it refuses to write when publication is disabled or another crawl remains active. A changed snapshot requires another crawl. Telegram completion reports include total crawl duration; a dry-run result includes no SHA, and a publication success includes only a confirmed SHA.

To compare a dry-run without Git credentials or a write to the public site, run `node dist/cli.js export --run-id <id> --output-dir /absolute/new-directory`. The command rebuilds and verifies the saved draft hash before creating a new directory containing `README.md`, `ui/src/data/repos.json` and `ui/src/data/stats.json`. It refuses an existing directory or a destination inside `ui/`. Point a separate staging checkout at these files for UI checks. Export does not change run metadata or call Git; opening the database still checks and, when needed, migrates the SQLite schema.

Set `DB_PATH` and `GITHUB_READ_TOKEN` for crawls. The read token authenticates GitHub API requests used to collect repository data; it raises the general REST API limit from 60 unauthenticated requests per hour to 5,000 authenticated requests per hour. GitHub code search has its own limit (10 requests per minute), so the token does not increase that bucket. `CRAWL_INTERVAL_HOURS` defaults to `24` and must be a positive integer. For publication, explicitly set `PUBLISH_ENABLED=true`, `GITHUB_PUBLISH_TOKEN` (distinct from the read token), `GITHUB_REPOSITORY=owner/repo`, `GITHUB_BRANCH`, `TELEGRAM_BOT_TOKEN`, and `TELEGRAM_CHAT_ID`. There is **no default repository or branch**. A lone Telegram credential is an error even in pilot mode; pilot without both credentials reports `notifier-disabled`. Never put tokens in command arguments or logs. The CLI logs safe categories instead of API response bodies. Snapshot validation errors also include the total issue count and up to 20 safe field paths; unexpected field names are omitted.

After every successful crawl, the CLI includes `report.discovery`, all `report.enrichment` outcome categories, `report.errorCategories`, `report.rateBuckets` and `report.durationMs` in its result. It saves this report in SQLite for a later `publish --run-id`. Telegram success/dry-run summaries include elapsed time, the outcome breakdown, up to five error categories and both request totals; full categories and ranges remain in SQLite and CLI logs. The separate `github_rate` JSON line also records `code_search` and `core` request attempts, cumulative wait milliseconds and last known remaining quotas even if a crawl fails. These counts contain no tokens or response bodies.

The active-run lock does not expire automatically: rate limits can keep a live crawl running many hours between heartbeat updates. When a *new* scheduled crawl finds `active_run` or `publication_locked`, it sends one Telegram failure per blocked run if configured; notification failure is logged and retried on the next start. This does not detect a still-running process: Railway skips the next cron event while that process is alive. Before cutover, arrange independent monitoring of active-process age and progress using Railway or another operator-approved service; set thresholds after the full pilot and verify delivery. If a run appears stale, first confirm in Railway that its process has stopped and back up the volume. Then run `node dist/cli.js recover-crawl --run-id <id> --confirm-stopped`. This marks only that running crawl as failed and records `operator_recovery`; it cannot bypass an interrupted Git publication. Do not infer process death from the heartbeat alone.

Publication holds a separate SQLite lease through Git PATCH and SQLite confirmation. A confirmed Git ref conflict retries from the new HEAD without traversing the history of the rejected commit; an ambiguous PATCH still needs ancestry reconciliation. A crash or ambiguous PATCH can leave the lease in place to prevent another crawl from publishing a conflicting stats ID. Check the pending SHA and the target branch against the volume backup, confirm the old publisher has stopped, then run `node dist/cli.js publish --run-id <id> --recover --confirm-stopped` with publication credentials enabled. This only takes over a lease for the same run; it checks the pending commit against the current target branch with GitHub's compare endpoint before attempting a write. Recovery therefore needs one ancestry request instead of walking commit history, regardless of how many commits separate the pending SHA and branch head. If the comparison is unavailable or indeterminate, stop and investigate the branch rather than editing SQLite or starting a new crawl. Migrating a v2 database with one pending commit places it behind this recovery lease; multiple pending commits require manual reconciliation before migration.

`openDatabase` accepts a local database path for development and tests. On Railway it requires an absolute `DB_PATH` inside `/data`, verifies that `/data` is a separate mount, and refuses to open the database otherwise. Mount the Railway volume at `/data` and set `DB_PATH=/data/catalog.sqlite` before using the database.
