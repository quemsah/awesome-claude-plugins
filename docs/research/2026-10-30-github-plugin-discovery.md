# GitHub API discovery for Claude Code plugin marketplaces

Research date: 2026-10-30

## Scope

A second discovery channel for **public repositories that host Claude Code plugin marketplaces**. It should discover candidate marketplace repositories, then let the crawler’s existing parser decide whether their entries are supported plugins. Exclude repositories that are only standalone MCP servers; MCP-related projects may still qualify when the repository is actually a plugin marketplace.

## First-party GitHub search behavior

- `GET /search/repositories` accepts the same query syntax/qualifiers as GitHub repository search. Terms search repository name, description, and topics by default; `in:name`, `in:description`, `in:topics`, and `in:readme` let a query target those fields. `in:readme` is the repository-search mechanism for README text; repository search cannot look through arbitrary files in the repository. [Repository search qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories) · [REST search endpoints](https://docs.github.com/en/rest/search/search)
- Search is useful for discovery, not exhaustive enumeration: GitHub documents up to **1,000 results per search**, a scope of up to **4,000 matching repositories searched** per query, query limits of 256 characters (excluding operators/qualifiers) and at most five `AND`/`OR`/`NOT` operators. Timeouts can return partial matches with `incomplete_results: true`. [REST search limits](https://docs.github.com/en/rest/search/search)
- Repository search returns at most 100 items per page (`per_page`, default 30). Follow the response `Link` header for pagination; ordinary REST pagination usually allows 100 items/page. The 1,000-result search ceiling means paging cannot reveal everything in an over-cap result set. [Search endpoint](https://docs.github.com/en/rest/search/search) · [REST pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)
- Search rate limits are separate from core REST API limits: authenticated search endpoints allow up to **30 requests/minute**, except code search; unauthenticated search allows **10/minute**. Core API authentication is normally 5,000 requests/hour, but this does not raise the tighter search quota. Read rate headers and honor `Retry-After`/reset; secondary limits also apply. [REST search limits](https://docs.github.com/en/rest/search/search) · [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- GitHub repository search can filter by `topic:...`, and repository metadata includes topics. Topics are a useful high-precision lane, but rely on repository owners applying them. `fork:true` can include forks; consider whether forks are useful for this crawler and dedupe by canonical repository identity. [Repository search qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories)

## Code search behavior and fit

- `GET /search/code` searches code terms with code-specific qualifiers (for example `filename:`, `path:`, `repo:`, `org:`, `user:`, `extension:`); repository-only qualifiers do not generally transfer to code search. It can help find repositories containing recognizable marketplace manifest paths or distinctive manifest keys, then those repositories must be fetched and validated. [REST code search](https://docs.github.com/en/rest/search/search) · [Legacy code-search syntax used by REST](https://docs.github.com/en/search-github/searching-on-github/searching-code)
- Code search is a costly secondary signal: **10 requests/minute**, requires authentication for REST API use, considers only default branches, excludes files >=384 KB, excludes archived repositories and repositories with >=500,000 files, and indexes repositories only if active or returned in search in the last year. These constraints make it unsuitable as the only discovery mechanism. [REST code-search constraints](https://docs.github.com/en/rest/search/search) · [Code-search indexing limits](https://docs.github.com/en/search-github/searching-on-github/searching-code)
- Code search is not a substitute for fetching a known candidate’s manifest: use repository contents/README endpoints after discovery to inspect marketplace configuration. Public repository contents and README can be read without authentication. [Repository contents and README endpoints](https://docs.github.com/en/rest/repos/contents)

## Bounded approach

1. **Run a fixed, versioned query catalog** against `/search/repositories`, with separate queries per field and language variant rather than one long boolean expression. Seed likely terms such as `claude code plugin marketplace`, `claude-code marketplace`, `plugin marketplace`, and format-specific manifest/registry language, using `in:name,description,topics`, `in:readme`, and dedicated `topic:` queries. Keep query terms curated and audit query yield over time.
2. **Partition only when useful.** For a query that approaches the 1,000 result cap, split it into non-overlapping `created:` or `pushed:` date windows, recursively narrowing crowded windows. Date qualifiers and `sort=updated` provide practical recency partitions; date windows can overlap at boundaries, so dedupe. Do not impose star thresholds as a completeness strategy because that discards small/new marketplaces.
3. **Bound each run explicitly:** cap query count, pages per query (never beyond the documented 1,000-result ceiling), wall-clock/API budget, and candidate fetches. Persist query/window, scan timestamp, counts, pagination completion, and `incomplete_results`; schedule incremental recent-`pushed:` scans plus a slower wider historical sweep. Fetch metadata/README/manifests only for deduplicated candidates. The crawler caps new/unprocessed marketplace candidates at 200 per run, rotates a persistent ID cursor so repeated failures do not starve later candidates, leaves the rest queued in the repository table, and reports how many were deferred.
4. **Use code search selectively** for a small number of high-signal manifest terms or filenames after repo-search yields are measured. Its separate 10/min quota, default-branch indexing, and file/repository eligibility exclusions make wide code-search sweeps poor value.
5. **Classify after retrieval:** require marketplace evidence (e.g. plugin marketplace manifest/catalog shape and plugin entries); reject standalone MCP servers as out of scope. Search terms alone are candidate generation, not proof.

This should broaden discovery and make each run reproducible and bounded. It **does not guarantee complete GitHub coverage**: repositories may omit relevant terms/topics, be newly created or not indexed yet, fall outside query/result/search limits, be archived or otherwise excluded from code search, or use unanticipated marketplace formats. Record misses and refresh queries rather than representing the feed as exhaustive.

## Bounded rollout audit (2026-10-30)

The crawler was exercised against an isolated in-memory SQLite database. No target repository was inserted manually, no production database was used, and no full crawl or historical backfill was run. Each scanner run was capped at 20 actual Repository Search HTTP attempts (`maxAttempts: 1` per page).

The generic catalog was revised to version 2 after inspecting the two missed repositories' public metadata. Topic queries now run before broad metadata and README queries; the catalog includes `topic:claude-plugin`, `topic:claude-code-marketplace`, `topic:claude-code-plugins`, and `topic:claude-code-plugin`. Rolling `pushed:` requests use `sort=updated&order=desc`; historical `created:` requests keep GitHub's default sort. These changes are reusable query and scheduling rules, not repository-specific exceptions.

The fourth run explains the remaining Mnemoverse miss: this audit did not finish the generic search partition containing its pushed date. It does **not** prove that GitHub's generic query cannot return the repository, nor that the repository is globally absent from search. A regression test now confirms that pending pushed leaves from earlier rolling roots are loaded on the next day's scan and exposed by `inspect`, so a moving 30-day root no longer discards their work. Mnemoverse's later discovery was not live-verified. A generic `claude-plugin` query family alone is not evidence of complete recall.

The final scan also sampled three discovered candidates through the existing marketplace gate: two were accepted with 1 and 3 plugin entries; one was rejected. Focused parser tests accept valid plugin catalogues and reject a standalone MCP server manifest without a plugin catalogue. Enrichment caps new/unprocessed candidates at 200 per run, advances a persistent candidate cursor, and leaves further candidates pending with the deferred count reported. At the run level either discovery channel can sustain progress; a zero-success Code Search result does not fail the crawl if Repository Search completed a partition or returned candidates, including a successful empty scan with no enrichment work. Pending leaves from earlier rolling roots are loaded on the next day's scan, and the scheduler alternates resumed leaves with newly generated rolling work so sustained saturated roots cannot continually consume the full request cap ahead of old leaves. Each due run reserves up to five of the 20 Repo Search requests for historical `created:` work after giving rolling `pushed:` queries up to 15 requests; unused historical capacity returns to rolling work. CorpusIQ was excluded throughout. No production backfill was started.

An auxiliary direct-query probe was attempted while diagnosing the catalog; its output was not retained and is excluded from the scanner funnel and recall claims. The recorded results above come only from bounded scanner runs.

## Follow-up: why Mnemoverse was missed and how to reduce recall gaps (2026-10-30)

### Confirmed eligibility and generic-query behavior

The public repository API reports `mnemoverse/claude-plugin` as non-archived, created on 2026-08-13, and pushed on 2026-10-30 at 13:10:39 UTC. Its description says it is a Claude Code plugin; its topics include `claude-plugin`; and its `.claude-plugin/marketplace.json` has one plugin entry. The GitHub page also shows the marketplace directory and install command. This is in scope for the crawler, and the discovery miss happened before marketplace enrichment could accept or reject it. [Repository API](https://api.github.com/repos/mnemoverse/claude-plugin) · [Repository page](https://github.com/mnemoverse/claude-plugin) · [Marketplace manifest](https://raw.githubusercontent.com/mnemoverse/claude-plugin/main/.claude-plugin/marketplace.json)

At 2026-10-30 16:22 UTC, I repeated generic Repository Search requests without an owner or repository-name qualifier. The `topic:claude-plugin` query for October 16–30 returned 1,183 matches; page 1 did not include Mnemoverse. Narrowing the same generic query to October 30 returned 291 matches; page 1 still did not include it, while page 2 returned it at position 37 (global position 137). A broader catalog metadata query returned 11,873 matches and also omitted it from page 1. Each response had `incomplete_results: false`. These requests were read-only and did not write or seed a repository into the crawler database.

This gives a concrete explanation for the earlier bounded audit: the catalog already had a matching generic topic, but the saturated date partitions consumed the request budget before the scanner reached the narrower October 30 partition and its second page. The target was not absent from the query vocabulary or rejected by the marketplace parser. GitHub's own docs describe Search as a relevance-oriented discovery endpoint, with a 1,000-result ceiling per query and at most 100 results per page; a matching query and a successful first page do not establish coverage. [Search API behavior and limits](https://docs.github.com/en/rest/search/search) · [Repository-search fields and qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories)

There was a second throughput risk in the implementation: it reset a partition's page count and restarted its page loop at page 1 on every attempt. Partition work survived the run cap, but page progress within an unfinished leaf did not. If the cap repeatedly landed after page 1, later pages could be postponed across runs even though the query matched the target.

### Follow-up implementation (2026-10-30)

The first fix is implemented in commit `c9dc624` (`fix(crawler): resume repository search pages fairly`):

- Schema v15 stores `next_page` for each repository-search partition. A partition stores its current page before the request and advances only after a successful response, so a transient failure retries that page and a run stopped by its request budget resumes after the last successful page.
- Unfinished leaves are ordered by least-recent attempt. `inspect` exposes `nextPage` with the existing state and `lastAttempt` fields.
- The cursor resets to page 1 if GitHub reports incomplete results, the advertised result count changes during a resumed search, or a short page appears before the expected end. Fully completed rolling `pushed:` partitions are still scanned again from page 1 on later runs to refresh recent results.
- Focused tests verify a synthetic page-two candidate, later-page retry after a temporary failure, cursor reset when counts change or a page is unexpectedly short, scheduling fairness, inspection, and migration. A focused live check then resumed the generic October 30 topic partition at page 2 in an isolated in-memory database and confirmed that the crawler stored `mnemoverse/claude-plugin` from the live result. It did not use an owner-qualified query or a seeded repository. No full 20-request crawl or production backfill was run. Commits: `c9dc624`, `6ea65e1`.

### Remaining recommendations

1. **Keep splitting saturated date ranges, then enumerate every page of each leaf.** The October 30 topic leaf had 291 results, so it was enumerable in three 100-result pages; the read-only generic API check found Mnemoverse on page 2. If a single-day leaf itself remains at GitHub's 1,000-result ceiling, add a second gap-free partition dimension (for example, repository creation-date ranges within a pushed-date window) and recurse until each leaf can be paged. Any extra dimension must have tests proving no gaps or overlaps.
2. **Consider an incremental public-repository feed as a separate long-tail source.** GitHub's `GET /repositories` endpoint lists public repositories in creation order and paginates using an exclusive repository-ID `since` cursor. After establishing a baseline and budget, it can surface newly created repositories independently of search terms; to catch unlabeled marketplaces, the crawler must inspect feed entries broadly enough to find their manifest. It does not find old misses until a backfill reaches them, and its high volume requires its own rate and processing budget. Search and this feed should both feed the same candidate/enrichment funnel, never an allow-list. [List public repositories](https://docs.github.com/en/rest/repos/repos#list-public-repositories)
3. **Use misses as generic-query regression cases.** Keep a small offline audit set outside production query configuration. For each case, record which generic query/page should discover it and whether the bounded scheduler reaches it within its target freshness window. Tests should use synthetic pages and must not hard-code repositories into the production catalog.

GraphQL Search does not remove the core issue: it has the same 1,000-result maximum, though it uses cursor pagination. Public Events are a weak supplement because GitHub caps the timeline at 300 events from the last 30 days and documents latency up to six hours. Webhooks are scoped to a repository, organization, Marketplace or Sponsors account, or GitHub App, so they do not offer a global repository-creation feed. [GraphQL Search limit](https://docs.github.com/en/graphql/reference/search) · [Public Events limits](https://docs.github.com/en/rest/activity/events#list-public-events) · [Webhook scope](https://docs.github.com/en/webhooks/about-webhooks)

**Conclusion:** durable page-level continuation and fair backlog scheduling are implemented, and a focused live crawler check retrieved Mnemoverse from page 2 without adding a repository-specific exception. A full capped crawl audit and production backfill were not run. The public-repository ID feed remains a separate follow-up for new-repository recall, with its own bootstrap and cost decision. Neither approach can support a claim of complete GitHub-wide historical coverage; report measured coverage and backlog age, and describe repository discovery as best-effort.
